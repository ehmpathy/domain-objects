# 🌙 dream: branch protection `allowsForcePushes: false` never sticks on ehmpathy/domain-objects main

- kind: reseed
- owner: ehmpathy/declastruct-github (suspected); ehmpathy/domain-objects (the drift)
- caught 2026-11-21

## .the cue that fired

the pr #144 provision plan showed `allowsForcePushes: true → false` on main's branch protection. main has declared `false` all along.

## .the gap, precisely

- main's `provision/github.repo/resources.ts` declares `allowsForcePushes: false`
- the last main provision run (run 34701224597, apply job 103573289558, 2026-09-12): plan `[UPDATE]` `"allowsForcePushes": true` → `false`, apply job `success`
- today (pr #144 plan, run 44880489488): remote still `"allowsForcePushes": true`
- so an apply that reports success does not write that field, or a later actor resets it. main stays open to force push despite its declaration

## .the shape of the fix

1. after the pr #144 merge, read the post-apply state: `gh api --method GET repos/ehmpathy/domain-objects/branches/main/protection --jq .allow_force_pushes.enabled`
2. still `true` → reproduce in declastruct-github: set branch protection with `allowsForcePushes: false` on a repo where it is `true`, then read back. if the read-back is `true`, the dao's update path omits `allow_force_pushes`
3. fix there, with a clamp: an integration test that flips it and reads it back

## .why it is not done in this round

the fix belongs to declastruct-github, and the proof needs a main apply (post-merge). this route only upgrades domain-objects. the upgrade moved declastruct-github 1.4.0 → 1.8.0, which may already fix it; step 1 tells.
