# 1.vision — `DomainObjectPragma` type + `kind` on the `.contract` pragma

> illustrate the world implied by `0.wish.md`: two additive upgrades to the
> `.contract` pragma shipped in domain-objects@0.32.0 —
> (1) publish a first-class `DomainObjectPragma` type (one type, optional keys, mirrors the
> stamp's own omit-when-absent shape), and
> (2) stamp the true `kind` (`entity` | `literal` | `event` | `object`) onto the pragma, so
> consumers stop a guess at the base class from a fragile `primary`-non-empty heuristic.

---

## ubiqlang: `pragma` vs `contract` vs `DomainObjectPragma`

> the pragma is what we **stamp**. `Dobj.contract` is the **stamped schema**. `DomainObjectPragma` is the **type of the pragma** — one type whose optional fields mirror the stamp's own omit-when-absent shape.

| term | what it is | who touches it |
|---|---|---|
| **`x-domain-object` pragma** | the raw json object stamped onto the schema via `.meta()` (`getContract.ts:86-95`) | the **originator**, at stamp time |
| **`Dobj.contract`** | the zod schema that holds the pragma | crosses the wire |
| **`DomainObjectPragma`** | the **exported type** of that pragma object — required `name`/`kind`, optional keys (present only when the dobj declares them) | the **consumer**, at codegen time |

the wish is: domain-objects owns the pragma → it should own the pragma's **type**
(`DomainObjectPragma`) and the pragma's `kind` too, instead of a re-declaration in every
consumer.

### 🧭 for future travelers: what "pragma" means, and the domain-object pragma family

> the name was hard-won. this section teaches the term so no one re-litigates it — and so the
> comment that declares the type can point future readers straight here.

**etymology — "pragma" = a matter of fact.** from Greek `πρᾶγμα` (*prâgma*), "a deed, a matter of
fact" (verb `πράσσειν`, *prássein*, "to do / to act"). adopted by C's **`#pragma`**: a directive
that is *a matter of fact for the compiler* — out-of-band from the program, it states how the
processor should treat the code. the general sense we use:

> **a pragma is a stated fact stamped alongside a payload, which declares how to interpret it.**

**the domain-object pragma family.** a schema node can state two different facts about its
domain-object semantics — so there are two pragmas, a base and a `Ref` partner:

| pragma (json keyword) | the fact it states | payload | type |
|---|---|---|---|
| `x-domain-object` | this node **IS** dobj X | X's class statics: `name`, `kind`, `primary`, `unique`, `alias`, `nested` | `DomainObjectPragma` |
| `x-domain-object-ref` | this node **REFERENCES** dobj X | `{ of, by }` — which dobj (`of`), by which key-set (`by`: `primary`\|`unique`\|`ref`) | `DomainObjectPragmaRef` |

**why `pragma` is the family name (not `Statics`, `Contract`, `Identity`, …).** the shared concept
across both is the **pragma** — the stamped matter-of-fact. what each *carries* differs (statics vs
a reference descriptor), so no content-word fits the family:

| candidate | why rejected as the family/base name |
|---|---|
| `…Statics` | honest for the base (it holds class statics) but a **misnomer for the ref** — `{ of, by }` are not statics (`by` is a reference-site choice). it names a payload, not the shared concept. |
| `DomainObjectContract` | **overclaims + collides.** a contract = schema **+** identity; the pragma omits the schema. it clashes with the `.contract` getter (returns a *schema*) and `src/contract/`. |
| `DomainObjectIdentity` | **too narrow.** `alias` (a colloquial label) and `nested` (structural links) are **not** identity. |
| `DomainObjectMeta` / `…Metadata` | **collides.** `DomainObject.metadata` is an extant static (`DomainObject.ts:154-178`) that means *instance persistence keys* — a different concept. |
| `DomainObjectDeclaration` | **ambiguous.** "declaration" is overloaded (var / type / `.d.ts` / import). |
| **`DomainObjectPragma` (+ `…Ref`)** ✅ | names the **shared concept** (the stamped matter-of-fact). the unmarked base + `Ref` qualifier **mirrors the runtime pair `DomainObject : Ref`** (`Ref.ts:29`) and the accessors `.contract` / `.contract.ref('primary')`. collision-free; the payload is documented, not crammed into the name. |

**the base/ref parallel is load-bearing.** the pragma names deliberately echo two extant pairs:

```
runtime:    DomainObject        :  Ref                    (Ref.ts — a Ref is a DomainLiteral of identity props)
accessor:   .contract           :  .contract.ref('primary')
pragma:     DomainObjectPragma  :  DomainObjectPragmaRef
```

the unmarked base = the primary type (like `DomainObject`); `Ref` = the one qualifier (like runtime
`Ref`). this is why the base is **not** `DomainObjectPragmaStatics` — a mark on the base would break
the parallel and re-introduce the payload-name problem.

### 🌱 term seed: the pragma family

- **`DomainObjectPragma`** — the base pragma type (on `x-domain-object`): "this node IS dobj X."
  holds X's class statics (`name`, `kind`, `primary`, `unique`, `alias`, `nested`) — the
  class-side half the instance schema/contract cannot carry, read only to **rebuild the class**.
- **`DomainObjectPragmaRef`** — the ref pragma type (on `x-domain-object-ref`): "this node
  REFERENCES dobj X." holds `{ of, by }` — the referenced dobj name + the key-set projected.

**the declaration comment.** the jsdoc on `DomainObjectPragma` (at its declaration) will carry the
etymology + the family table above in-line, so a future reader learns "pragma = a matter of fact"
at the exact point of first contact — no ambiguity, no need to hunt for this vision doc.

**one type per pragma, optional fields — no split.** an earlier draft split the base into a
stamp-truth type + a filled type + a fill transformer. dropped: a single `DomainObjectPragma` with
**optional** keys already tells the truth (the stamp omits absent keys, so the type marks them
optional). no second type, no fill step — the consumer reads `pragma.primary` as
`string[] | undefined` and applies `?? []` if it wants, honest to reality.

## the outcome world

### day-in-the-life

`sdk-aws-lambda` runs codegen. it converts an upstream endpoint's zod schema to
json-schema and finds the pragma on a field. **today** it must hand-roll a local
`DomainObjectPragma` type and *infer* the base class:

```ts
// sdk-aws-lambda, today — invented type + fragile inference
import type { DomainObjectPragma } from './domain.objects/DomainObjectPragma'; // local, invented
const kind = (pragma.primary ?? []).length > 0 ? 'entity' : 'literal'; // guess
```

**after** both asks land, it imports the shape and reads the truth:

```ts
// sdk-aws-lambda, after — shared type + stamped truth
import type { DomainObjectPragma } from 'domain-objects';
const pragma = pragmaNode as DomainObjectPragma; // typed by the shared type
const kind = pragma.kind; // 'entity' | 'literal' | 'event' | 'object' — stamped, not inferred
```

### before / after

| | before | after |
|---|---|---|
| the pragma type | each consumer re-declares `DomainObjectPragma` locally | one exported type from domain-objects |
| entity vs literal | inferred from `primary`-non-empty (fragile) | read from stamped `kind` (exact) |
| a literal that declares `primary` | **misclassified as entity** | correctly `literal` |
| an entity without `static primary` | **misclassified as literal** (pragma omits `primary`) | correctly `entity` |

### the "aha"

the getter already holds the real `dobj` class — it *knows* whether it extends
`DomainEntity`, `DomainLiteral`, or `DomainEvent` via the marker symbols on the class
(`markers.ts:7-12`). so it can **stamp the truth once** instead of a proxy signal every
consumer must reverse-engineer. and once the pragma is authoritative, its **type** is a thing
domain-objects should publish once, not leave each consumer to re-declare.

## user experience

### usecases / goals

| persona | goal |
|---|---|
| downstream codegen (`sdk-aws-lambda`) | import one `DomainObjectPragma` type; read an exact `kind`; delete the local type + inference |
| any future consumer | speak the same pragma-type shape instead of a local re-declaration |
| upstream author | no change — `kind` rides for free from the class they already declared |

### contract inputs & outputs

**ask 1 — the published surface (one type, optional fields):**

there is a **core tension** the wish's single always-present type hides: `getContract`
deliberately **omits** absent fields (`getContract.ts:88`, `...(dobj.primary ? {primary} : {})`),
yet the wish's local type declares `primary`/`unique` as **always-present** `string[]`. the
honest fix is **one** type whose optional fields mirror the omit-when-absent stamp — required
where the stamp always writes, optional where it may skip:

```ts
export type DomainObjectPragma = {
  name: string;                                    // always stamped
  kind: 'entity' | 'literal' | 'event' | 'object'; // always stamped (from class marker)
  primary?: string[];                              // omitted when absent → optional
  unique?: string[];
  alias?: string | { singular?: string; plural?: string };
  nested?: Record<string, string | string[]>;
};
```

the type now tells the truth in its own shape — no fill step, no second type. the consumer
reads `statics.primary` as `string[] | undefined` and applies `?? []` if it wants the filled
view. this decision replaces the earlier two-type split (`DomainObjectPragma` + filled
second type + a fill transformer) — dropped as over-engineering.

**no fill transformer either.** with optional fields there is no field to fill, so
a fill transformer earns no keep. the only parse a consumer needs is to
read the `x-domain-object` node off the json-schema — a plain property access on `unknown`, not
a domain-objects concern. so ask 1's published surface is **just the type**
(`DomainObjectPragma`); the "ideally a transformer" part of the wish is dropped (see open-q5).

**ask 2 — the stamped field:**
- `getContract` adds `kind` to the pragma it assembles (`getContract.ts:86-92`):
  ```js
  const pragma = { name: dobj.name, kind: getKind(dobj), ...primary, ...unique, ... };
  ```
- `kind` is stamped from the class's marker symbols, **not** from `primary`.

### what leveraging it looks like

```ts
// upstream — unchanged; kind rides automatically
const out = z.object({ job: Job.contract });
const json = z.toJSONSchema(out);
// json.properties.job['x-domain-object'] = { name:'Job', kind:'entity', primary:['uuid'], ... }

// downstream — read the node, typed by the shared type
import type { DomainObjectPragma } from 'domain-objects';
const pragma = json.properties.job['x-domain-object'] as DomainObjectPragma;
// pragma.kind → 'entity'   pragma.primary → ['uuid']   pragma.unique → undefined (omitted)
```

### timeline

1. author declares the dobj once (statics + `static schema`, already done).
2. at endpoint declaration, `.contract` stamps `name` + **`kind`** + keys.
3. codegen converts to json-schema → pragma carries `kind`.
4. consumer reads the node as `DomainObjectPragma`, picks `DomainEntity<T>` vs
   `DomainLiteral<T>` (vs `DomainEvent<T>`) from `kind` directly.

## mental model

- **describe to a friend**: "the shipping label on the schema now says *what type of thing*
  it is — an entity or a value — instead of making the receiver guess from whether it has
  an ID field. and we ship the receiver a standard form to read that label."
- **analogy**: the `_dobj`/`x-domain-object` label already carried the *name*; now it also
  carries the *species* (`kind`). and we publish the field guide (`DomainObjectPragma`)
  so every reader classifies the same way.
- **precedent**: mirrors the extant pragma-stamp pattern (`getContract.ts`) and the
  `isOfDomainEntity` / `isOfDomainLiteral` marker-walk (`inherit/isOfDomainEntity.ts:10-21`)
  — lifted from instance-level to class-level.

| they say | we say |
|---|---|
| "entity vs value/literal vs event" | `kind: 'entity' \| 'literal' \| 'event' \| 'object'` |
| "the class's static declarations" / "what you need to rebuild the class" | `DomainObjectPragma` (the exported type) |
| "read the label" | property access on the `x-domain-object` node, typed `DomainObjectPragma` |

## evaluation

### how well it solves the goals

- **ask 1 (published type)**: ✅ one exported `DomainObjectPragma` type (optional keys);
  consumers delete their local copy. no transformer — no field to fill.
- **ask 2 (real kind)**: ✅ stamped from class markers — exact, not inferred. kills both
  misclassification directions.
- **additive / no breaks**: ✅ `kind` is a new pragma field; the consumer's inference
  fallback still works until it upgrades. `DomainObjectPragma` is a new export.

### pros

- **exactness**: `kind` comes from the subclass identity, the source of truth.
- **shared vocabulary**: one type across all consumers; no drift between hand-rolled copies.
- **zero author boilerplate**: kind rides from the class already declared.
- **consistent with extant marker infra**: reuses `MARK_AS_DOMAIN_*` symbols.

### cons / costs

- **`kind` is a 4-value union, so the consumer's switch must cover all four.** decided as
  `'entity' | 'literal' | 'event' | 'object'` (open-q1) — honest to the library's four classes.
  the cost: the consumer's base-class pick must handle `event` (→ `DomainEvent<T>`) and the rare
  `object` (plain dobj), not just the binary the wish first framed.
- **the published type's field names are a small standard we own** — `DomainObjectPragma`'s
  optional-key shape + field names become a compat surface (open-q2).
- **class-level marker detection** must walk static inheritance correctly (a subclass of a
  subclass of `DomainEntity` must still read `entity`). low risk — static symbols inherit —
  but must be tested with a 2-level subclass.
- **the param type must gain the marker keys.** `getContract`'s param is the structural
  `DomainObjectClass` (`getContract.ts:23-30`), which declares **no** marker-symbol keys. to
  read `kind`, that type must be extended with the optional marker-symbol keys (e.g.
  `[MARK_AS_DOMAIN_ENTITY]?: string`) so detection type-checks **without** an `as` cast
  (`rule.forbid.as-cast`). the runtime value already carries the symbols; only the type is
  behind. an execution wrinkle, not a blocker — but a real one the impl must honor.
- **resist a `DomainObjectPragma` modeled as a `DomainLiteral` class.** the dogfood urge
  tempts us toward a runtime dobj (with its own schema), but a plain exported TS
  `type`/`interface` suffices, adds no runtime weight, and matches the consumer's hand-rolled
  `interface`. keep it a type.

### edgecases & pit-of-success

| edgecase | why it matters | pit-of-success contract |
|---|---|---|
| **`DomainLiteral` with `static primary`** | real today: `Sandbar` in `getContract.test.ts:145-152` is a literal with `primary:['uuid']` — the wish heuristic calls it `entity` | marker-based `kind` stamps `literal` correctly |
| **`DomainEntity` without `static primary`** | pragma omits `primary` (`getContract.ts:88`) → heuristic sees no primary → `literal` | marker-based `kind` stamps `entity` correctly |
| **`DomainEvent`** | 3rd real class, has identity; not entity, not literal | marker-based `kind` stamps `'event'` (decided: `kind` is a 4-value union) |
| **plain `DomainObject` w/ schema** (`Seafoam`, `getContract.test.ts:233`) | no entity/literal/event marker at all | marker-based `kind` stamps `'object'` (decided: the base-class fallback value) |
| omitted fields in pragma (`unique`/`alias`/`nested` absent) | `getContract` omits absent fields | `DomainObjectPragma` marks those keys **optional** — `pragma.unique` is `string[] \| undefined`, honest to the stamp |
| consumer on old domain-objects | `kind` absent | additive — consumer's `primary` fallback still fires |

## open questions & assumptions

### assumptions

1. `kind` should be derived from the **class marker symbols** (`MARK_AS_DOMAIN_ENTITY` /
   `MARK_AS_DOMAIN_LITERAL` / `MARK_AS_DOMAIN_EVENT` / `MARK_AS_DOMAIN_OBJECT`), not from
   `primary`. verified these are static symbols that inherit down subclasses
   (`DomainEntity.ts:31`, `DomainLiteral.ts:30`, `DomainEvent.ts:30`).
2. the published `DomainObjectPragma` is **one type with optional keys** — required
   `name`/`kind`, optional `primary`/`unique`/`alias`/`nested` (present only when stamped).
   excludes `shape` (see q2). field-name spelling subject to the alignment the wisher invited.
3. **no transformer.** the earlier fill-transformer step is dropped — with optional
   keys there is no field to fill (see q5).
4. **additive for read-by-key consumers — but NOT a zero-diff change.** `kind` adds no field
   the consumer must read; its inference fallback still fires. *however*, "no consumer break" is
   too strong: any reader that asserts the pragma by **exact match** breaks. this includes the
   repo's own tests (`getContract.test.ts:62-68`, `:155-160`, `:241-243` use
   `expect(pragma).toEqual({...})`) and every `.contract` snapshot — all must update. so the
   honest claim is: additive at the field level, a break at the exact-equality level.
5. `kind` is minification-safe. unlike the pragma's `name` (`constructor.name`, mangleable —
   prior vision assumption #4), `kind` is a fixed literal (`'entity'`/`'literal'`/`'event'`/`'object'`),
   so it carries **no** part of `name`'s bundler fragility. a strict improvement, not a shared risk.

### open questions (triaged)

1. **`[answered]` `kind` union = `'entity' | 'literal' | 'event' | 'object'`.** wisher decided
   (2026-07-18): stamp the truth for all four classes from their marker symbols —
   `entity`/`literal`/`event` for the three subclasses, `object` for a plain `DomainObject`
   with a schema but no subclass marker (the `Seafoam` edge, `getContract.test.ts:233`). the
   consumer's base-class switch handles the extra values (`DomainEvent<T>` for `event`; `object`
   is the rare plain-dobj case). chosen over the binary + mapping because it loses no fidelity.
2. **`[answered]` field names mirror the class statics.** wisher decided (2026-07-20): keep each
   pragma key spelled identically to the class static it comes from — `name`, `kind`, `primary`,
   `unique`, `alias`, `nested` (mirror `DomainEntity.primary`, `DomainObject.alias`, `.nested`,
   …). zero translation, and it's what `getContract` already emits. **`shape` stays excluded:**
   domain-objects stamps identity only (`getContract.ts:86-95`); the `shape: JSONSchema` field in
   the consumer's local type is the outer json-schema node the pragma rides on, not part of what
   we stamp.
3. **`[answered]` the pragma node is read as-is; no transformer.** with optional keys the consumer
   reads the `x-domain-object` node directly, typed as `DomainObjectPragma` — a plain property
   access on the json-schema node. no fill/parse step to place. (superseded the earlier
   "transformer input boundary" question — there is no transformer.)
4. **`[answered]` malformed-pragma handling is the consumer's read-site concern.** with the
   transformer dropped, domain-objects ships only the type; a consumer that reads a malformed node
   handles it at its own boundary (fail-fast per `rule.require.failfast` remains the recommended
   posture, mirroring `getContract`'s own `ConstraintError` at `getContract.ts:72-83`). no
   domain-objects runtime to write here.
5. **`[answered]` ask-1 ships the *type only*; the transformer is dropped.** wisher decided
   (2026-07-18): domain-objects publishes what is unambiguously ours — `kind` (ask 2) + the
   `DomainObjectPragma` **type** (ask 1). the "ideally a transformer" fill/parse step is **not**
   built: with optional keys there is no field to fill, and the node-read is a plain property
   access the consumer owns. this resolves the earlier ownership tension — we ship the type, not a
   consumer-ergonomics transformer.
6. **`[answered]` base type name = `DomainObjectPragma`.** wisher decided (2026-07-19). names the
   type by the **shared concept** (the stamped matter-of-fact), not a payload — because a second
   pragma (`DomainObjectPragmaRef`) exists, and no content-word (`Statics`, `Identity`) fits both.
   the unmarked base + `Ref` qualifier mirrors the extant `DomainObject : Ref` runtime pair and the
   `.contract` / `.contract.ref(...)` accessors. beats the rejected candidates (`Contract`
   overclaims + collides; `Identity` too narrow; `Meta` collides with `DomainObject.metadata`;
   `Declaration` ambiguous; `…Statics` a misnomer for the ref). see "🧭 for future travelers."
7. **`[answered]` one exported type per pragma, not a split.** wisher decided (2026-07-18): a single
   `DomainObjectPragma` with **optional** keys mirrors the omit-when-absent stamp honestly — no
   stamp-truth-plus-filled split, no fill transformer. the earlier two-type split is dropped.
8. **`[cross-team]` `DomainObjectPragmaRef` — the ref pragma type.** a peer branch found it needs to
   stamp `x-domain-object-ref: { of: string, by: 'primary' | 'unique' | 'ref' }` onto `Ref*` schema
   nodes ("this node REFERENCES dobj X"). this vision adds the **base** pragma; the ref pragma is its
   partner (see the family table). the shape (`{ of, by }`) and the base-name choice
   (`DomainObjectPragma`, unmarked) are jointly owned across three parties: **this branch** (base +
   `kind`), the **ref-pragma peer** (the `Ref*` stamp), and the **sdk-aws-lambda consumer** (imports
   the base type). the names must land coherently — **align before either merges.** confirm too that
   the accessor is `.contract.ref('primary')` (the `Ref`/`RefByPrimary`/`RefByUnique` runtime types
   exist, `Ref.ts:29`), so the pragma names track the real accessors.

### external research

the wish references no external APIs — this is a library-surface feature building on the
extant `.contract` getter. zod-4's `z.toJSONSchema()` verbatim-passthrough of `.meta()`
keys is already proven and shipped in 0.32.0 (see prior behavior
`.behavior/v2026_06_30.schema-getter/1.vision.yield.md` q6). **none — no new external
dependencies.**

### internal research

verified against the extant code the wish extends:

- **the pragma assembly**: `getContract.ts:86-92` builds `{ name, ...primary, ...unique,
  ...alias, ...nested }`, omitting absent fields via spread. `kind` slots in here.
- **the getter passes the real class**: `DomainObject.contract` → `getContract(this)`
  (`DomainObject.ts:108-110`). so at runtime `getContract` receives the actual constructor
  with marker symbols in its static chain — detection works even though the *type*
  (`DomainObjectClass`, `getContract.ts:23-30`) is structural.
- **kind-detection primitive is extant**: `isOfDomainEntity` / `isOfDomainLiteral` walk the
  marker symbols (`inherit/isOfDomainEntity.ts:10-21`), but on **instances**
  (`obj.constructor`). the class-level analog reads the static symbol directly off `dobj`.
- **markers** (`markers.ts:7-12`): `MARK_AS_DOMAIN_ENTITY`, `MARK_AS_DOMAIN_LITERAL`,
  `MARK_AS_DOMAIN_EVENT`, `MARK_AS_DOMAIN_OBJECT` — all `Symbol.for(...)`, statically
  inherited by subclasses (`DomainEntity.ts:31`, `DomainLiteral.ts:30`, `DomainEvent.ts:30`).
- **the four classes**: `DomainObject` (base, `DomainObject.ts:42`), `DomainEntity`
  (`DomainEntity.ts:22`), `DomainEvent` (`DomainEvent.ts:21`, abstract), `DomainLiteral`
  (`DomainLiteral.ts:21`). `DomainLiteral.primary` is **optional** (`DomainLiteral.ts:41`) —
  the concrete proof the `primary` heuristic is unsafe.
- **the smoking-gun test case**: `getContract.test.ts:139-157` — `Sandbar extends
  DomainLiteral` with `static primary = ['uuid']`. its pragma is `{ name:'Sandbar',
  primary:['uuid'] }`; the wish's heuristic would misread it as `entity`.
- **export surface**: `src/index.ts` is the barrel of record — the `DomainObjectPragma` type
  lands here alongside `isOfDomainEntity` et al.
- **vocab to reuse**: `kind`, `x-domain-object`, `pragma`, `MARK_AS_DOMAIN_*`,
  `ConstraintError` fail-fast.

## what is awkward?

1. **`object` is the soft edge of the `kind` union.** `entity`/`literal`/`event` map cleanly to
   the three subclass markers, but `object` is the fallback for a plain `DomainObject` that has a
   schema yet no subclass marker (`Seafoam`, `getContract.test.ts:233`). it is a real value
   (decided, open-q1), but it names an "unclassified dobj" more than a peer of the other three —
   a mild taxonomy wrinkle the consumer's switch must still handle.

2. **~~the type-name collides with `.contract`~~ — resolved by the `DomainObjectPragma` name.**
   an earlier draft named the type `DomainObjectContract`, which collided with the `.contract`
   getter (returns a *schema*) and `src/contract/` — a real mis-read trap (one would expect
   `typeof Dobj.contract`, a schema, but get the class-side declarations). the name
   `DomainObjectPragma` (open-q6, decided 2026-07-19) removes the collision: "pragma" names the
   stamped matter-of-fact, and reserves "contract" for the schema the getter returns. it also
   scales to the ref partner (`DomainObjectPragmaRef`, open-q8). see "🧭 for future travelers" for
   the full name-discovery. no residual awkwardness here.

4. **"pragma" is a tool-flavored word — but taught at the declaration.** naming the public type
   `DomainObjectPragma` elevates a compiler-ish term into the api surface. accepted deliberately:
   "pragma" is the established word (the wish + `getContract` already speak it), it names the shared
   concept across the base + ref family, and its one cost — a reader who does not know the word — is
