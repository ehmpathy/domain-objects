# 1.vision — structural multi-option disambiguation (no `_dobj` tag required)

> fulfills ehmpathy/domain-objects#124

## how it works, in one breath

for a nested key with multiple options, on a plain input object:

1. **`_dobj` present?** → use it directly (explicit wins; skip the rest).
2. else **try each option** — the one whose schema accepts the input is the match. any option that accepts the input must declare a **strict** (closed) schema; else **failfast**.
3. **exactly one match** → use it. **zero** → throw "no option fits". **many** → throw "ambiguous, add `_dobj`".

**totally additive**: the no-`_dobj` multi-option path throws today ("can not determine which option"), so every new outcome here — clean match *or* a sharper failfast — replaces a throw with a throw or a success. no case that succeeds today changes. `_dobj`-first also keeps every extant `_dobj` / schemaless setup untouched; try-each is purely the no-tag fallback. full order-of-operations table below.

## the outcome world

### day-in-the-life

an author hand-writes a domain object whose nested key accepts **two structurally-distinct options**. today they hit a wall — a plain nested object throws unless they hand-set a `_dobj` discriminator they never think to write. after this fix, they just write the natural shape and it hydrates into the right option automatically.

concrete, seaturtle-themed — same world as the related bare-array-skip PR (the real downstream driver is declastruct-aws's `[Principal, PrincipalScope]`, see groundwork). here our multi-option case lets `forage` accept **two different domain objects**, one of which itself nests the other:

```ts
// SeaturtleForageSpecies — a species the turtle forages, keyed by slug
interface SeaturtleForageSpecies { slug: string }
class SeaturtleForageSpecies extends DomainObject<SeaturtleForageSpecies> implements SeaturtleForageSpecies {
  public static schema = z.object({ slug: z.string() }).strict();
}

// SeaturtleForageScope — a different domain object: include/exclude lists of species
interface SeaturtleForageScope {
  include: SeaturtleForageSpecies[];
  exclude: SeaturtleForageSpecies[];
}
class SeaturtleForageScope extends DomainObject<SeaturtleForageScope> implements SeaturtleForageScope {
  public static schema = z.object({
    include: z.array(SeaturtleForageSpecies.schema),
    exclude: z.array(SeaturtleForageSpecies.schema),
  }).strict();
  public static nested = { include: SeaturtleForageSpecies, exclude: SeaturtleForageSpecies };
}

// Seaturtle — forage can be either domain object
interface Seaturtle { forage: SeaturtleForageSpecies | SeaturtleForageScope; name: string }
class Seaturtle extends DomainObject<Seaturtle> implements Seaturtle {
  public static nested = { forage: [SeaturtleForageSpecies, SeaturtleForageScope] };
}
```

### before / after

```ts
// BEFORE — throws NestedDomainObjectHydrationError
new Seaturtle({
  forage: { slug: 'seagrass' }, // no _dobj → "can not determine which option"
  name: 'crush',
});

// BEFORE — the only way that worked
new Seaturtle({
  forage: { _dobj: 'SeaturtleForageSpecies', slug: 'seagrass' }, // author must hand-tag
  name: 'crush',
});

// AFTER — just works; { slug } validates only against SeaturtleForageSpecies
const turtle = new Seaturtle({
  forage: { slug: 'seagrass' },
  name: 'crush',
});
turtle.forage instanceof SeaturtleForageSpecies; // true

// AFTER — the other option too; { include, exclude } validates only against SeaturtleForageScope
const squirt = new Seaturtle({
  forage: {
    include: [{ slug: 'seagrass' }],
    exclude: [{ slug: 'jellyfish' }],
  },
  name: 'squirt',
});
squirt.forage instanceof SeaturtleForageScope; // true
squirt.forage.include[0] instanceof SeaturtleForageSpecies; // true — nested option hydrates too
```

### the "aha" moment

the value clicks when the author realizes the **shape itself is the discriminator**. they never needed a tag — the two options don't overlap, so the library can just try each and see which one fits. `_dobj` stops being a chore for the common case and becomes a fallback for the genuinely ambiguous case only.

## user experience

### usecases & goals

- **hand-author polymorphic nested objects**: write the natural shape for a multi-option nested key, no discriminator ceremony.
- **keep safety on ambiguity**: when a shape could be more than one option, still get a loud, clear error rather than a silent mis-map.
- **preserve deserialize path**: `serialize`/`deserialize` still stamp and read `_dobj`, so round-trips are unaffected.

### contract inputs & outputs

no signature change. same `hydrateNestedDomainObjects` / `DomainObject` constructor surface. the behavior of the **multi-option branch** changes.

order of operations (first match wins, top to bottom):

| # | input to a multi-option nested key | outcome |
|---|---|---|
| 1 | already an instance of a valid option | keep it (unchanged) |
| 2 | plain object **with `_dobj`** | use `_dobj` directly — skip try-each, no schema checks (unchanged) |
| 3 | plain object, no `_dobj`, an option **that validates the input is absent or non-strict** | **failfast**: "structural disambiguation needs a strict schema on every option — add strict schemas, or pass `_dobj`" (**new**) |
| 4 | plain object, no `_dobj`, exactly **one** strict option validates | hydrate into that one option (**new**) |
| 5 | plain object, no `_dobj`, **zero** options validate | throw "no option fits" |
| 6 | plain object, no `_dobj`, **many** strict options validate | throw "ambiguous, disambiguate via `_dobj`" |

**`_dobj` is checked first (step 2).** when the explicit discriminator is present, we never run try-each — the author's intent is unambiguous, and we skip the construct-and-validate of every candidate. try-each (steps 3-6) is purely the fallback for plain objects that carry no `_dobj`.

**strict is mandatory to trust a match (step 3).** to trust "validates → matches", the option's schema must be closed (reject unknown keys). a non-strict schema lets a *superset* object validate against a subset shape → false match. so whenever an option **validates the input**, that option must be strict; if a schemaless or non-strict option validates, we failfast and demand strict schemas (or `_dobj`). a strict schema makes "validates" mean "structurally fits exactly".

**why "an option that validates", not "every option"** (decided 2026-07-06): strictness is detected by a lib-agnostic behavior-probe — add an unknown key to the input and check whether the schema still accepts. this probe is only meaningful against an object the schema already accepts; for an option that does *not* validate the input, there is no accepted object to probe, so its strictness is undetectable without per-lib schema introspection (zod catchall, joi unknown flag, yup noUnknown — the fragile route we rejected). this loses no runtime safety: a superset object can only be mis-mapped into an option whose schema *accepts* it, and every option that accepts the input is strict-checked. an option that never validates the input can never receive it, strict or not.

this order keeps schemaless options back-compat: schemaless + `_dobj` settles at step 2 (never reaches try-each); schemaless + no `_dobj`, when the schemaless option validates the input, hits step 3 (failfast — which today already throws, so still additive).

### what it looks like to leverage

```ts
// exactly-one-match → auto-picked
new Seaturtle({ forage: { slug: 'seagrass' }, name: 'crush' });                       // → SeaturtleForageSpecies
new Seaturtle({ forage: { include: [{ slug: 'seagrass' }], exclude: [] }, name: 'crush' }); // → SeaturtleForageScope

// ambiguous → clear error, points to _dobj
new Seaturtle({ forage: { /* fits both */ }, name: 'crush' });
// → NestedDomainObjectHydrationError: "...ambiguous... disambiguate via _dobj or instantiate explicitly"
```

### timeline

instantiation-time only. try-each runs once per nested prop during construction; the first (and only) validating candidate is kept and assigned.

## mental model

- **users say**: "it figures out which type my object is from its shape."
- **we say**: "structural disambiguation via try-each-option validation, with `_dobj` as the tiebreaker for ambiguity."
- **analogy**: a mail sorter reading the *shape* of an envelope. a letter and a parcel go to different bins with no label needed; only when two things look identical do you need a written tag.
- term reuse: `_dobj`, `nested`, `options`, `hydrate`, `NestedDomainObjectHydrationError` — all extant vocab, no new terms introduced.

## evaluation

### how well it solves the goal

directly. the multi-option case (`[SeaturtleForageSpecies, SeaturtleForageScope]`, no shared keys — mirrors the downstream declastruct-aws `[Principal, PrincipalScope]`) resolves cleanly with zero discriminator. strict `_dobj` safety is retained precisely where it matters (ambiguity).

### pros

- removes discriminator ceremony for the common structurally-distinct case.
- backwards compatible: instance inputs, `_dobj` inputs, and single-option inputs all behave as before.
- fail-loud on both zero-match and ambiguous-match — no silent mis-mapping.

### cons / tradeoffs

- try-each **instantiates candidates** to test them — for N options that means up to N construction+validation passes for one prop. cost is bounded by option count (small) and only on the multi-option branch.
- disambiguation power depends entirely on **schemas being present and discriminating**. options with no schema never throw on validation → they always "match" → every multi-schemaless case is ambiguous and falls back to `_dobj` (which is exactly today's behavior — see back-compat note).

### edgecases & pit-of-success

| edgecase | how the contract keeps users safe |
|---|---|
| options without schemas (on the try-each path) | **failfast** at step 3 when the schemaless option validates the input — can't structurally disambiguate without a strict schema; error says add strict schemas or pass `_dobj`. schemaless + `_dobj` is untouched (settles at step 2, as the extant `PlantPot`/`PlantBed` test relies on). |
| **non-strict schema** — a superset object validates against a subset shape | **closed by design**: step 3 failfasts whenever a non-strict option validates the input, so a superset can never silently match. authors must declare strict schemas (or use `_dobj`). settled via the strict-schema requirement (see open questions q4). |
| array-valued nested key with mixed options | each element runs try-each independently; same rules apply per element |
| candidate construction has side effects | none expected — construction is pure validate+assign; but worth noting try-each constructs then discards non-winners |

## open questions & assumptions

### assumptions

1. options under a multi-option nested key that authors want auto-disambiguated **carry schemas** — otherwise no signal distinguishes them. (grounded: the constructor only validates when a schema is present — `DomainObject.ts:46` `if (schema && ...)`; `validate` itself is skipped entirely without one.)
2. the intended discriminator is **schema validation pass/fail**, exactly as the issue's pseudocode states.
3. preserving the extant `_dobj` and single-option behaviors is required (back-compat). (grounded: the extant test `DomainObject.test.ts:274-302` uses `_dobj` with schemaless options.)

### open questions — triaged

1. **[answered] core disambiguation rule**: follow the issue exactly — try each option, collect matches by schema validation pass/fail; exactly-one → use it; zero → throw "no option fits"; many → `_dobj` fallback, else throw "ambiguous". answered by the issue's own pseudocode; no wisher input needed.
2. **[answered] `.build` vs `new`**: keep `.build(prop)` for the candidate that wins. resolved by logic + code: the single-option path (`hydrateNestedDomainObjects.ts:74`) and `_dobj` path (`:127`) both use `.build`, so the winner must too, for immute parity. the issue's `new` is illustrative pseudocode, not a constraint.
3. **[answered] enumerate matched options in the ambiguous error**: yes — include the matched option names in the error metadata. resolved by logic: cheap, high debug value, consistent with the extant error's message + metadata format (`hydrateNestedDomainObjects.ts:6-17`).
4. **[answered — wisher decided] strict schema is a hard requirement, not a nudge**: to use structural disambiguation (the no-`_dobj` try-each path), an option that validates the input must declare a **strict/closed** schema. if a schemaless or non-strict option validates the input, we **failfast** (step 3) with a clear error — add strict schemas, or pass `_dobj`. this eliminates the superset over-match footgun by construction rather than by after-the-fact ambiguity detection. decided by the wisher on 2026-07-05.
   - **scope refinement (2026-07-06)**: the failfast fires per option **that validates the input**, not eagerly across every declared option. strictness is checked by a lib-agnostic behavior-probe (add an unknown key; see if the schema still accepts), which is only meaningful against an object the schema accepts. this loses no runtime safety — a superset can only be mis-mapped into an option whose schema accepts it, and every option that accepts the input is strict-checked — while it avoids fragile per-lib schema introspection. decided by the wisher on 2026-07-06.
   - **cross-lib note (blueprint)**: "strict/closed" is per-schema-library — zod `.strict()`, joi's default unknown-key rejection (i.e., not `.unknown(true)`), yup `.noUnknown()`. the behavior-probe detects "closed" uniformly across libs without per-lib code.

**note on the wisher's `z.alternatives` aside**: the wisher asked whether upstream needs `z.alternatives`. that concerns how a *downstream* consumer declares its own combined zod schema for the polymorphic field — orthogonal to this library change. our `nested` array of options is the domain-objects mechanism; a consumer's zod schema for the same field is their choice. not a dependency of this fix.

## what is awkward?

- **try-then-discard**: constructing candidates purely to test validity, then throwing away the losers, feels wasteful. it's the simplest faithful implementation of the issue, and cost is small (option count), but it's not elegant. an alternative — validate against `ClassOption.schema` directly without constructing — avoids the discard but skips nested hydration during the test and diverges from the "instantiate" framing. flag for the blueprint stage.
- **the schema dependency is now explicit, not silent**: an author who wants auto-disambiguation on schemaless options hits the step-3 failfast with a clear "add strict schemas or pass `_dobj`" message — no confusing "ambiguous" mystery. the strict requirement turned an implicit gotcha into a loud, actionable error.
- **strictness is a real ask on authors**: to opt into try-each, an option that validates the input must carry a strict/closed schema. that's a deliberate cost — the wisher chose it (2026-07-05) to close the superset over-match footgun by construction rather than tolerate silent mis-maps. authors who don't want it keep using `_dobj`.
- **"strict" is per-schema-lib**: the closed-schema check differs across zod/joi/yup, so the failfast's detection logic is a blueprint concern, not a one-liner.
